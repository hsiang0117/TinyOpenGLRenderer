# 代码阅读规则

本文用于指导后续新增代码与分步整理，目标是让读者从入口、接口和数据名称理解流程，减少跨文件反推约定。

这里的规则不代表当前源码已全部满足。文中的候选函数名均为命名示例，不表示已有接口，也不要求在一次修改中统一全库。

## 整理边界

- 保持现有渲染行为、资源失败处理、容量保护与 OpenGL 上下文释放顺序。
- 一次整理围绕一个明确职责或一组接口，避免同时改变算法、所有权和文件布局。
- 优先使用现有类、普通函数和小型数据结构，不为可读性引入框架。
- 格式调整服务于理解，不以代码行数、文件数量或注释数量衡量效果。

## 主流程先表达意图

入口函数应先让读者看到执行阶段、先后依赖和失败出口，再进入阶段内部的实现。

例如，命名示例 `beginInputFrame()`、`pollEvents()`、`publishPendingResources()` 分别表达输入快照、事件轮询和资源发布，避免不同阶段都只叫 `update()`。

提取步骤时应保留必要上下文：在哪个线程执行、是否需要当前 GL 上下文、结果从何时开始生效。
不要把有先后依赖的操作拆成无法看出执行顺序的回调或分散的隐式副作用。

## 按职责拆分

函数同时处理导入、坐标转换、资源创建和错误展示时，优先按这些职责建立边界。
提取后的函数名应说明结果或动作，参数应能看出所需输入；避免只有 `handle()`、`process()` 的通用步骤名。

文件按共同用途和变化原因组织，不按固定行数拆分，也不要求一类一文件。
多个简单光源组件可以放在同一组；具有独立生命周期或复杂行为的功能可以单独成组。

主流程保留协调步骤，细节实现放到对应模块。不要为了缩短函数而产生必须来回跳转才能理解的碎片。

## 头文件表达契约

头文件首先展示调用方需要知道的接口、数据含义和生命周期约束。
内部遍历、递归、校验及中间转换步骤默认私有；只有确有外部调用需求时才公开。

对存在隐含条件的接口，说明以下相关内容即可，不为简单访问器重复模板化注释：

- 输入是否允许为空，借用对象需要存活多久。
- 调用线程、GL 上下文与初始化阶段要求。
- 返回值表示成功、未就绪还是允许回退，失败后哪些状态仍然有效。
- 是否允许重复调用，以及操作即时生效还是延迟提交。

返回只读视图时，说明其有效期与失效条件。`const` 容器中的可变指针不自动构成只读对象视图。
头文件包含与前向声明遵循[头文件依赖约定](header-dependencies.md)。

## 配置、有效状态与缓存

区分用户正在编辑的配置、已应用的资源状态和可以重建的派生数据。
命名示例 `materialDraft`、`activeMaterial`、`boundsCache` 用于体现这种差别，不规定必须采用这些名称。

简单独立参数可以公开，例如颜色和变换分量。需要同步更新 AABB、GPU 资源或错误状态的修改应经过统一入口，避免公开字段绕过该入口。

候选资源通过验证后再替换当前资源；失败时保留现有可用状态的规则应在接口处清楚表达。
缓存由维护该缓存的模块负责失效，调用方不应手动修改另一个对象的私有缓存。
若仅允许对象入场景前组装组件，应显式表达这个阶段边界；需要运行时修改时，由场景协调修改和视图失效。

## 所有权与借用

- 值成员和 `unique_ptr` 表达独占管理；`shared_ptr` 用于确实需要共同延长生命周期的对象。
- 引用表达调用期间必需存在的借用；可为空的指针应说明缺省行为。
- 保存的非拥有指针或引用，应说明拥有者以及销毁顺序要求。
- 观察可独立销毁的共享对象时，可使用 `weak_ptr`，避免观察关系延长其生命周期。

不要仅因函数需要读取对象就改变其所有权。查询接口优先表达只读语义，需要修改时由名称和参数明确说明。
系统依赖尽量在一个可见的组装步骤中建立，避免调用方依靠多次 setter 猜测对象何时可用。

## 语义命名与计算边界

名称说明领域含义，遵循[命名约定](naming.md)，避免只做大小写和缩写替换。
同一状态词保持同一含义：例如就绪表示可以使用，待处理表示尚未提交；不要用同一个 `Ready` 标志同时表示初始化成功和需要失败清理。

自有 C++ 类型、函数和常量归入 `togr`，现有用途命名空间保留在根下。全局入口显式限定项目名称；第三方声明与 include 留在其原作用域，不能依靠全局 `using namespace` 隐去边界。宏使用项目专属前缀，细则见[命名空间约定](naming.md#c-命名空间)。

涉及变换时说明来源与目标空间。命名示例 `meshToModel` 比 `transform2` 更容易与乘法关系核对。
对坐标、距离、角度和时间注明必要单位，尤其区分局部/模型/世界空间、度/弧度、秒/动画 tick。

CPU 数据导入、后台计算、主线程 GPU 上传和资源发布是不同阶段，应从接口名称、类型或契约中看出边界。
保留 UTF-8 文本与原生文件路径的转换边界，不让日志、编辑缓冲区和文件操作各自猜测编码。
已有坐标与路径约定以[项目文件组织](project-structure.md)为准。

## CPU/GPU 数据协议

业务参数与 GPU 传输布局分别表达，通过具名打包入口转换；整理时保持既有对齐、步长和字段布局约束，不引入代码生成。
C++ 的 `sizeof`、`offsetof` 与 GLSL 字段应双向对照，任一侧变更都同步检查另一侧。绑定槽、向量通道和哨兵值使用有语义的名称。

共享协议定义可以供程序与测试共用；独立参考测试应按契约构造预期结果，不调用被测打包实现生成预期值。

## 排版与注释

后续新增或整理的自有 C++、GLSL 按以下规则排版，随所整理模块逐步应用；本轮文档不表示源码已全部重排：

- 使用 4 个空格缩进，不使用 Tab。
- 函数和控制语句的左花括号与声明或条件同行。
- 非平凡控制流使用大括号，例如含嵌套判断、多步操作或资源状态修改的分支。
- 一行一个主要操作，资源创建、状态修改、判断和返回不挤在同一行。
- 空行分隔执行阶段与独立步骤，不用连续空行人为扩大文件。
- 自有文件使用 UTF-8、Windows CRLF；已有 BOM 保持原状，第三方文件保持原样。

局部变量名与作用域应贴近实际用途，不复用参数充当另一种含义的游标。

简单前置条件可以提前返回；复杂失败应保留原因和清理责任，不能为缩短主流程删除保护。
注释优先解释单位、空间、兼容原因和不变量，不逐句翻译代码，也不记录已经结束的调试过程。
中英文术语保持同一概念的表达一致；无需为本轮整理开展全库翻译或引入格式化工具。

## 验证行为

结构调整应通过现有行为回归，验证调用方可观察的结果和失败后状态。
测试主体按准备、操作、断言组织，一个清楚的行为对应一个具名检查；公共夹具负责场景搭建，具体检查负责场景判断。
涉及数学或渲染结果时，使用独立参考值、明确的场景约束或 GPU 输出检查，避免测试只重复实现公式。
失败路径检查应包括原资源是否保留、无效资源是否被使用，以及销毁是否仍发生在有效上下文中。

按影响范围选择编译与回归；不为低影响排版建立重复实现的测试，也不以单次构建成功代替行为验证。
报告区分已执行检查与尚未验证的效果，不把静态推断当作画面证据。

## 同步阅读导航

入口、职责或生命周期改变时，同步更新[主流程与功能导航](code-reading.md)，让推荐阅读顺序继续对应实际源码。
文件移动同步[项目文件组织](project-structure.md)、工程项和 VS 筛选器；名称与依赖变化同步相关约定及调用方。

阅读指南记录当前实现；本文记录后续整理遵循的规则。两者都应使用可定位的文件与接口，避免将候选设计写成现状。
